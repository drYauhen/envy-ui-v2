## Context

Envy UI is expected to scale into a multi-tenant system where each client can have a customized UI, CMS-driven semi-static websites, and report templates, potentially generated by AI. This requires:

- Per-client theme customization without breaking the shared system.
- Safe automated generation of tokens that preserve accessibility and consistency.
- A delivery model that supports many client-specific variants.
- Domain-specific requirements (e.g., legal, finance, healthcare, avionics) with stricter compliance or validation rules.
- Different validation levels for app UI, website CMS templates, and reports (screen vs print).
- Cultural and country-specific UX requirements (i18n/locale rules, RTL, regional readability norms).

The current token architecture already separates foundation, semantic, context, and theme layers. A forward-looking strategy is required to allow per-client overrides without destabilizing the core system or requiring full rebuilds for each tenant.

---

## Decision

I decided to treat **canonical tokens as versioned source code** and define **tenant-specific tokens as override patches**:

1. **Canonical source remains Git + DTCG JSON**  
   The core token layers (foundations + semantic + core component defaults) are versioned in Git and remain the single source of truth.

2. **Tenant overrides are patch layers**  
   Client-specific customization is expressed as small JSON patches that override only allowed paths (typically context/theme/component variants). Overrides must remain DTCG-compliant and can be scoped by domain or locale rulesets.

3. **AI generates overrides, not raw CSS**  
   AI is constrained to produce token deltas inside approved schemas. These deltas are validated (contrast, range limits, required fields) before acceptance. Validation levels may differ by domain and output channel (app UI, CMS website, report).

4. **Build pipeline composes outputs**  
   A build step compiles `base + overrides` into `tokens.css` (and any JSON/figma exports) per tenant/theme. The compiled bundle is what apps consume.

5. **Optional database as delivery layer**  
   A database may store tenant overrides for runtime delivery and querying, but canonical tokens stay in Git. The DB is a distribution layer, not the source of truth.

---

## Rationale

- **Scalability:** Overrides are small and only touch upper layers. This enables hundreds of client variants without duplicating the entire token system.
- **Stability:** Foundations remain stable, reducing the risk of AI-generated changes breaking core semantics.
- **Auditability:** Token deltas are reviewable, versioned, and comparable.
- **Consistency:** Shared validators enforce contrast rules and naming patterns across generated variants.
- **Compliance readiness:** Domain-specific and locale-specific validation profiles can enforce stricter thresholds (e.g., legal readability, safety-critical UI, print/PDF rules, RTL or regional typographic norms).
- **Future readiness:** Enables generative UI, CMS templates, and reports while keeping strict system constraints.

---

## Consequences

- A formal **override schema** and validation rules are required (e.g., allowed paths, contrast thresholds, range limits).
- **Domain/locale validation profiles** are required to apply stricter rules for regulated sectors, regional requirements, and report outputs.
- A **composition pipeline** is required to generate per-tenant bundles from base + patch.
- Tenant-specific metadata (non-visual `.meta.json`) can remain alongside overrides for documentation/agent use.
- New tooling may be required for preview and change review of per-tenant token sets.

---

## Notes

- Overrides should remain scoped to context/theme/component variants and avoid foundation edits.
- The contrast strategy defined in [ADR-0031](ADR-0031-contrast-strategy-dynamic-colors-on-color-tokens.md) applies to AI-generated overrides.
- Domain/locale profiles can include additional compliance checks (e.g., minimum font size for reports, print-safe palettes, sector-specific constraints, RTL or regional typographic rules).
- This ADR does not mandate a specific database vendor; any JSON-capable store can be used for delivery.
